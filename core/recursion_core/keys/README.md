# keys: user-entered API keys

Recursion keeps the model-provider API keys a user types in. It keeps them in the OS keychain where there is one, and in an owner-only file on a host with none. A key is never logged, never put in a prompt and never sent to CSL. Engine sign-ins (Claude Code, Codex) stay in each engine's own store and are never read here. Any vendor's key can be kept. This package is the store, its commands and the credential source that lets an API-key route run.

## Commands

The same four actions are available as `python -m recursion_core.keys ...` (which needs no daemon) and, once `recursion-control` reads SPINE's command table (S2), as `recursion-control key ...`. SPINE's seams are on master and `hooks.py` registers the family there, but master's `recursion-control` does not read that table yet:

| Command | What it does |
|---|---|
| `add ID --provider VENDOR --env VARIABLE` | Reads the key from the terminal with echo off. It asks whether runs on this key may spend money billed to it, and the cap in US dollars. `--stdin` reads the key from standard input instead, and only when that is not a terminal; `--allow-metered-spend --cap-usd N` answers the spend questions up front. A key is never read from the command line. |
| `list [--json]` | Ids, providers, variable names, save times, the store, the spend opt-in, and any unfinished operation. It never shows a value. |
| `remove ID [--yes]` | Asks first (`--yes` skips the question), then deletes the key and says from where. It also clears what an interrupted save left behind, and a value of an id no saved key has that the store's own owner-only file still holds (its index lost, emptied or put back), whatever the host offers now. |
| `audit [--path P] [--no-journal]` | Looks for every saved value in Recursion's state and config folders, the given paths and the user journal. It names each place a value was found, never the value, and any temp file an interrupted save left in the store's folder. It names each id whose value the owner-only file holds and no saved key names, and says when that file is not the store's own; on the Secret Service it counts the items Recursion saved there that no saved key names. Its last line counts the saved keys and, apart from them, the values it looked for. It exits 1 when one was found, 4 when the search was incomplete (a value or a file could not be read, an operation is unfinished, the journal was asked for and not searched to the end, or the Secret Service holds items no saved key names), and 3 when it was refused. |

- **`ID`** is the route's connection id (`route.connection.id` in `routes.json`). It must start with a letter or digit, be at most 64 characters, and not look like a key: no word (letters and digits between `.`, `_`, `:` and `-`) longer than 16 characters, none of more than 11 that mixes letters and digits, no more than 8 digits in a row, and no more than 4 changes between lower case, upper case and digits inside its words. `codex-key`, `login-B`, `gpt4o-mini` and `claude-3-5-sonnet-20241022` are ids; `AKIAIOSFODNN7EXAMPLE`, 32 hex digits, `abcdefgh12345678` and `sk-ant-api03-Ab3d-Ef5h` are refused, without being repeated. A key of one case of letters only, in words of at most 16, cannot be told from a name and is accepted.
- **`VARIABLE`** is the variable the engine reads the key from: `ANTHROPIC_API_KEY` for Claude Code, `CODEX_API_KEY` or `OPENAI_API_KEY` for Codex.
- **`VENDOR`** is any lower-case vendor id: 1 to 64 of `a-z 0-9 . _ -`, starting with a letter or digit. Eight are published, one per vendor whose API key the product contract names, and lane ROUTING routes those: `anthropic`, `openai`, `google`, `xai`, `cursor`, `opencode`, `nous` and `refuseless`. The list, with the contract line behind each id, is `PROVIDERS` in `validate.py`. A key saved for any other vendor is kept and listed, but it is handed to no engine until its vendor is published (`provider_unrouted`). No route or grant can name a vendor yet, so nothing could tell that a route is meant for that key.

Anything else typed after `key` is refused and not repeated, so a key pasted on the command line by mistake does not come back in an error.

## Where keys are kept

The index, `$XDG_CONFIG_HOME/recursion/keys/index.json` (default `~/.config/recursion/keys/`), holds the metadata and never a value. The values are in the backend:

- **Linux with a Secret Service on the session bus:** the Secret Service, through `secret-tool`. The key goes in on its standard input and comes back on its standard output, never in its arguments or environment. Without `secret-tool` (package `libsecret-tools`), the store refuses rather than write a file. KWallet is used through its Secret Service interface; with that interface off, the store refuses rather than write a file. A removal counts as done only when `secret-tool lookup` finds nothing and `secret-tool search --all` (which lists locked items too) lists nothing; otherwise it is refused and the key stays listed.
- **No session bus, or a bus with no keychain on it:** the owner-only file `secrets.json` beside the index.
- **macOS and Windows:** their keychain backends are not built yet, so the store refuses there instead of writing a file.

**Files.** The folder is 0700 and every file in it is 0600, owned by the user. All of this is checked on every open, through the descriptor that was opened. Symlinks are refused and not followed, and a FIFO cannot block a read. Writes go through a temp file, fsync and rename, with the folder's lock held exclusively. Reads hold it shared, so a read never sees a key change halfway (see `files.py`). The index holds at most 1 MiB and the owner-only file 4 MiB; a save that would exceed either is refused (`store_full`) before anything changes. A temp file left by an interrupted write is deleted by the next save or removal.

**Identity.** A store is its folder, however the folder is spelled. Its id, which names its items in the keychain, is random and recorded in the index at the first save, so every path that reaches the folder (`..`, a symlinked parent, a trailing slash, a bind mount, another letter case where the file system ignores case) opens the same index and reaches the same values; a relative folder is refused.

**Binding.** Each save also gets a random id of its own. The value is stored with the store's id, that save id and the record's provider: as attributes of the keychain item, or beside it in the owner-only file, whose header also names the store. A value is handed out only when all three match the record being used. So an older `index.json` put back, or an edited record, gets `secret_missing`, never another save's value. An index copied in from another store's folder carries that store's id: on a keychain it reaches that store's own values through that store's own records; on the owner-only file it reaches nothing. A copy of the whole folder carries the store's id too: on a keychain both copies name one set of items, so a removal through either deletes the value the other's record names; on the owner-only file each copy has a file of its own, and the two part at their first write. An owner-only file without these ids is refused. A file naming another store hands nothing out, is never written over while this index has keys, and does not block a removal. A removal deletes every value saved for the id in the store.

**Values no saved key names.** An index lost, emptied or put back no longer names every value the store holds. A save, a removal or a recovery changes the values of the id it names and of no other, so such a value is never deleted by an unrelated command. The store's own owner-only file is the one in its folder, except while its keys are in a keychain (then it has none) or in the file (then only a file that names the store's id). With no saved key, the file in the folder is the store's own whichever store it names, whatever the host offers, even beside an `index.json` that kept its store id: the same folder is the same store (a save into the file takes its store id; a store on a keychain keeps its own). A value in its own file stays there: `audit` searches for it and names its id; `remove ID`, for an id no saved key has, deletes it whatever the host offers now, and changes nothing else (it takes no store id); and `add ID` into the file is refused until it is removed, so no save replaces a value it was not given. A file that is not the store's own (one naming another store while the store has keys in the file, or any while its keys are in a keychain) is never changed by it: `audit` searches for the values of one it can read and says the file is not the store's, and names one it cannot read as unreadable (the audit is then incomplete); its values go only through their own store or with the file. A file of the store's own that it cannot read refuses the audit, as every command that reads the file refuses it (`list` reads only the index, and a save into a keychain never reads the file): a value with no binding beside it is refused, never guessed at. With no saved key that is the folder's file on any host; a save into the keychain or moving the file away ends it. A store whose keys go in the owner-only file and that has no keys takes the file's store id at its next save. A store on a keychain never takes it, and never reads the owner-only file to save or hand out a key, nor to remove one while its keys are there. On a keychain an item is named by the store's id, which only `index.json` records: if `index.json` is lost, the store cannot name its items any more, so it can neither hand them out nor remove them. `remove ID` of a saved key deletes every item of that id in the store, whichever save stored it. `audit` counts every item Recursion saved in the keychain that no saved key names by its save (nor an unfinished operation by its id), and is incomplete while there is one; the keychain's own tool finds them by the attribute `application recursion`.

**Pinning.** The first save records the backend the host offered then. Every later operation that touches a value refuses when the host now offers a different one: `keychain_unavailable` when the keychain is gone, `backend_changed` otherwise. A key pinned to a keychain is removed where that keychain answers, since its removal must reach the value. A key pinned to the owner-only file is removed whatever the host offers now, so once a keychain appears, keys are moved by removing them and adding them again; a file in the owner-only file's place that the store did not write (a folder, a symlink, another shape) is refused, as by every command that reads the file. A locked keychain is refused (`keychain_locked`) and is never answered from the file. The pin is released when nothing is left.

**Unfinished operations.** An add or a removal records its intent in the index before it touches a keychain or the file. If the outcome is not certain (the keychain helper was killed or ran out of time and the keychain cannot say it holds nothing, or the process was killed), the intent stays:
- `list` shows it;
- the key is refused (`operation_pending`), whether or not its add had finished;
- the next save or removal finishes or undoes it;
- `remove ID` clears it on request.

An intent records the save it was written for (`save_id` in `index.json`), and a recovery, or the rollback of an add whose last index write failed, deletes only that save's value: an older `index.json` put back can carry an intent whose id was saved again since, and that newer value stays. An intent written before intents carried a save id is read as it is: with a saved key beside it, the key's own save is the one; with none, it is finished only when the store verifiably holds no value of its id, and otherwise stays (refused `operation_pending`) until `remove ID` clears it.

**Names shaped like keys.** `add` refuses a provider (`provider_invalid`) or a variable name (`env_name_invalid`) that has the shape of a key, by the same rule as a key id, and does not repeat it, so a key pasted into `--provider` or `--env` is not written to `index.json` or shown by `list`. An `index.json` that already holds such a name is still read.

## The credential source

`credentials(connection_id, env_name)`, imported as `from recursion_core.keys import credentials`, is the `Credentials` type of `routes/base.py`. It returns the value only when the id is saved under exactly that variable name and the key has a spend opt-in with a cap above 0. An unknown id, or a known one asked for under another name, raises `KeyError(connection_id)`, as the daemon's default does. A refused known id, or one whose add or removal is unfinished, raises `KeyRefused`, a `KeyError` with a typed code. Either way the route refuses before launch: `launch_refused`, "no credential for ID". It is the only way a value leaves the store for a route; `KeyStore.values()` serves `audit` alone.

`hooks.py` registers it into seam S7, and the `key` command family into S2, when SPINE's `control.hooks.compose()` loads this lane. The seams are on master, but nothing outside them calls `compose()` yet: until the daemon and `recursion-control` call the composed hooks, the daemon still passes `no_custody` and every API-key route refuses, as before.

## Spend

Each key records `metered_spend_allowed` and `cap_usd`, entered at `add`. With no opt-in the cap is 0, and every run on the key is refused before launch until it is removed and added again with one. Lane QUOTA enforces the cap; until it does, the provider console's spend limit is the hard stop.
